# Forge 1.20.1_GTL：合并物料分量分析的重复扫描

本轮以 `0625d62` 为基线，合并 `CraftPlannerV2.analyzeLowWidthComponents` 中两次遍历相同配方及输入的工作。适用环境：Minecraft 1.20.1、Forge 47.1.3、Java 17、Windows x64；分支 `1.20.1_GTL`。

## 实现与正确性

在计算每个物料分量的边界宽度和可建模副产物时，同时收集配方并计算求解准入、顺序重放要求和不可行证明资格。删除原来的独立元数据扫描，以及保存配方和三个布尔状态的四张临时 Map。分量仍按既有 `componentSequence` 顺序创建；物料顺序、配方顺序、副产物身份语义和外部需求/供给计算保持一致。

有限耐久工具仍由原有回退路径处理。返回输入、容器余项、私有可复用库存、不安全副产物和反馈引导仍限制其所属分量的顺序验证及证明资格。没有改变精确算术、求解预算、分量耦合条件或集合容量。

新增两项端到端回归：九次合成使用寿命为四次的工具，工具充足时使用三件，只有两件时报告一件短缺；两种情况均与独立双路线递推分量组合，并交换根输入顺序。两条工具路线共享同一工具库存，确保工具不足场景进入分量分析而非先被乐观容量证明拒绝。断言独立分量完成一次精确求解、回退路线选择和库存数量正确。

初版工具不足夹具使用一条无工具的缺料路线，没有进入预期的分量求解路径，导致新增断言失败。独立 JVM 对照确认基线和候选行为完全一致；随后修正夹具，生产代码未因此改动。首次 104 项定向执行中的这次失败、修正后的执行和全部压测原始数据均保留在配套 JSON 中。

## 压测方法

基线与候选共享已构建类及依赖，仅在类路径首项覆盖各自独立编译的 `CraftPlannerV2` 和内部类。Java 17、G1、256 MiB 初始堆、2 GiB 最大堆、4 个活动处理器。每个版本分别运行三个独立 JVM，交替版本顺序；压测与 Gradle、GameTest 分开执行。

4096 分支完整规划分别请求 1 与 10¹²，每个 JVM 预热一次、测量五次，调用方截止时间 15 秒。普通规划夹具覆盖长链、宽图、会话、无关项目及准入；独立证书作为未改动路径的对照。这两类夹具每个 JVM 预热三次、测量十二次。

独立 `BigInteger` 供给顺序重放检查实际库存、每步消耗和最终产量，其开销不计入耗时及线程分配量。所有预热失败、缺失与预算退出均保留；18000 宽图的预算退出是准入夹具的预期结果。

两版本完整规划各 30 个测量样本及六次预热均可行，没有预算退出，全部通过独立重放。独立证书各 72 个测量样本及 18 次预热均可行；普通规划全部通过相应核验，准入夹具各 36 个测量样本按预期退出预算。

数量 1 的完整规划及部分链/会话场景耗时更慢。普通线性规划和独立证书没有经过本轮修改的分量分析，其耗时变化作为对照记录，不归因于本轮优化。本轮仅报告分配量中位数的改善，不宣称整体提速。
