# 补料验证预算与排序拓扑复用

## 问题

`MaterialDagBudgetTest.refinementKeepsTheSmallerSupplementAndItStillReplansWithMinimalSearch`
偶发返回 `{M2=6}`，而相同图补 `M2=5` 可重新规划执行。
阶段诊断显示：外层缺料细化已有 100 ms 上限，内部材料排序又取剩余时间的四分之一，
首个更小补料验证通常只获得约 25 ms。内部超时后回退的最小递归搜索没有验证成功，
细化遂保留原补料。该时刻搜索次数及求解器工作量预算仍有余量。

## 修复

- 补料探针内部的材料排序不重复四等分已有时间片；普通规划仍保留原来的时间预留。
- 保留外层细化 100 ms、材料排序累计 100 ms、120 次排序尝试、24 次补料探针以及共享工作预算。
- 从原会话复用已完成的配方排序拓扑，每个补料探针重新投影库存并计算供给上界；
  不复用含旧库存的 `PreparedGraph`，不同探针的补料不累加。
- 保留原库存下供给为零的拓扑，因为补料可能启用这些路线；当前库存的 `maySupply` 仍拒绝零供给。
- 可选超时或工作量耗尽保留已经完整构建的支持，不丢弃其证明再重复排列。
- 复用的部分拓扑不是不可行证明；没有找到可行计划时，只有相同累计时间、次数和工作量预算仍允许，
  才回退到补料库存下的编译。切换拓扑时清除按索引缓存的准备数据。
- `PlanningExitException` 和用户取消继续传播，真正的外层预算退出仍保留上一个安全补料方案。

## 回归覆盖

原失败用例断言不变，新增测试检查：

1. 内部安装的 deadline 不再比父细化 deadline 提前约四分之三。
2. 补料验证中的用户取消传播及作用域恢复。
3. 真正过期的细化阶段保留可执行补料。
4. 零库存支持补料后可用，连续不同补料不污染原图或上个探针。
5. 刷新消耗共享工作预算、保留原副产物配方身份。
6. 排序中途超时保留已完成支持，并能重新补料投影。

隔离的修复前类运行新增 deadline 回归会失败，修复后的正式类通过。
因此不是删除断言或简单重跑掩盖原错误。

## 原 PR 的 Forge 验证范围与限制

最终实现的自然模拟：10 个独立 JVM 共 160 次串行规划，以及 4 个 JVM 各 8 线程共 256 次规划，
均未再次返回 `{M2=6}`；每次补料后以最小递归搜索重新规划，物料平衡检查全部通过。
这是本机样本，不证明任何负载下都能获得最小补料。

额外注入一次 30 ms 调度暂停的 8 次最终对照中，7 次仍获得更小补料，1 次外层细化耗时约 129 ms，
超过保留的 100 ms 窗口，安全回退到 `{M2=6}`。该结果如实保留；有限 wall-clock 预算下，
调度暂停仍可能造成改善质量退化，不能把可选预算退出与证实不可行混为一谈。

模拟针对 Java 17 / Forge 1.20.1 工程类输出，未新增游戏客户端验证。开发日志和详细样本只保存在忽略的

### 基准方法

沿用[规划器优化文档](v2-feasible-consumption-optimization.zh-CN.md)的独立 JVM、串行 ABBA/BAAB 口径：

- 每个平台、每类测量启动 8 个 JVM，顺序为修复前、后、后、前、后、前、前、后；每个端点各 4 个。两版分别使用 Java 17、Java 21，参数均为 `-Xmx3g -Xss16m`。
- 使用已有 TBR1 配方投影及固定目标、库存清单，不重新生成输入。Vanilla、Small、NAST、ATM 各 48 查询，共 192 查询；每端点在独立 JVM 中重复两次。
- 大图计时选取 random20 库存下 NAST 的 `mekenergistics:me_supreme_combining_factory` 和 ATM 的 `pneumaticcraft:kerosene`，请求量均为 100,000；每 JVM 每数据集预热 8 次、采样 8 次。
- 六个小图对照每场景预热 500 次、采样 500 次。补料场景取 `MaterialDagBudgetTest` 的 `sharedCycle` 和 `batchCycle`，目标均为 `M6 × 2`，每场景预热 20 次、采样 40 次。
- 大图与小图对照沿用 2,000,000 的 `thunderbolt.maxReachablePlanningWork` 和 `thunderbolt.maxCraftSearchWork`；补料循环使用默认预算。
- 两个端点以已验证构建的类快照为基础，替换并使用相同 javac 参数重新编译各自提交的 `CraftPlannerV2`、`MaterialDagOrders` 及嵌套类；其余生产类相同。输入、源码和编译类均记录哈希，结束后再次核对输入未变。
- 计时仅覆盖规划调用，排除解析、构图和结果校验。墙钟耗时与分配量先取各 JVM 样本中位数，再取 JVM 间中位数。CPU 原始计数另存；短调用受线程计时粒度影响，不用其百分比推断收益。

### 正确性与结论

- 两个平台共 1,536 次语料查询，修复前后的支持状态、可行性、预算截止、库存使用、缺料及配方执行次数均一致；其中 992 个可行计划通过库存、物料平衡与执行回放。不可行或预算受限结果不作为不可行性的数学证明。
- 1,920 次补料循环调用（包含预热）均将返回缺料加入原库存，以最小递归搜索重新规划，并通过独立的原始配方逐次执行回放。
- 正式采样中，每个平台每端点的共享循环 160 次均返回 `{M2=2}`，批量循环 160 次均返回 `{M3=1}`。alpha 修复前 80 次共享循环预热中有 2 次 `{M2=4}`、1 次 `{M2=5}`；修复后均为 `{M2=2}`。较保守的补料也通过执行验证。
- 本次样本中，补料循环中位耗时下降约 4%–14%；共享循环分配减少约 6%，批量循环分配增加约 5%。ATM、NAST 两个固定请求的中位耗时变化均在 ±1% 内。
- 结果支持保留修复：未发现正确性退化，补料热点有局部收益，但没有整包普遍提速证据。有限墙钟预算下仍可能得到较保守补料，不保证任意负载下全局最小补料。

TBR1 是文档定义的单产物物料投影，不代替 AWR v3 加权多产物适配器、真实机器执行或整合包 TPS 测量。此处 192 查询使用已有的 2026-10-04 目标/库存清单，不等同于更早历史报告的查询集。本轮未新增客户端或游戏服务器实测。
