# Item 字段与双层弱规范化缓存

本次迭代接续对象复用实验 `caa258c`，保留 AE2 的值相等、hash、网络及存档语义。普通物品走 Item 字段；组件物品走身份索引和内容规范化两层缓存。流体仍使用原有有界缓存。本次没有修改规划器算法。

## 普通物品

注册 Item 经 Mixin 实现 `ItemKeyCacheOwner`，保存当前缓存代的 holder。空组件 patch、继承 NeoForge 默认容量／最大耐久／当前耐久钩子的物品，可以直接读字段返回原生构造的 AEItemKey。

一个 `volatile AEItemKey` 槽直接存放在 Item 上，普通命中走 `Item → key`。启用键复用时，Key 内部栈统一为 count=1、popTime=0；数量和动画既不参与普通槽分流，也不参与组件内容探针、身份别名或通用缓存索引。调用方原栈不变，实际数量由存储清单／执行计划保存，`toStack(n)` 仍生成 n 件。

普通命中通过 Key 上的 prototype 快照字段核对模板身份，避免重复读取 Key → ItemStack → 组件映射。试验中的 32 B 方案增加了普通热路径代价，因此按热路径优先的要求恢复这一字段；组件 Entry 反向引用继续移除。holder 用于组件缓存及代次管理。自定义 Item 覆写钩子时继续核对动态元数据；按数量计算的元数据也基于归一化的单件栈，避免输入 64 件与 Key 的 1 件状态不一致。构造入口覆盖网络／存档等原生路径，关闭 `reuseAeKeys` 后恢复原生数量／动画行为。

首次使用仍经过原生构造，采用懒初始化，不在物品注册尚未完成时抢先构造。Item 默认实例可能自带组件，例如药水，不能把 `of(item)` 和 `of(new ItemStack(item))` 强行合并。

配置重载、清空和停服时会拆除旧 Item 字段；换代后拒绝在途请求重新挂回旧 holder。Key 发布与拆除在同一个 Item 监视器内检查 holder 身份和当前代次，避免旧构造线程晚返回覆盖新槽；清理旧代也不能清除已经发布的新代。构造器和物品钩子仍在锁外运行。普通槽强持有的对象数受已注册物品数限制，不为任意组件变体保留强引用。

这是字段位置调整，没有把 Item 改造成 AEItemKey 子类。AE2 19.2.17 中 AEItemKey 是 final 具体类，私有构造器要求已构造的 ItemStack；普通 Mixin 添加接口无法让 `Item instanceof AEItemKey` 成立。该方向需要改写继承、构造链及键状态，超出本次保持 AE2／附属类型契约的优化范围。

## 通用 WeakCanonicalMap

最简单的用法：

```java
record Value(String content) {}
var values = new WeakCanonicalMap<String, Value>(Value::new);
var first = values.get(new String("same"));
assert first == values.get(new String("same"));
```

也支持独立身份 token、整数变体、延迟构造内容 key、有效性校验和共享 L1 表。该类仅依赖 JDK。

1. **L1 身份索引**：对不可变快照 token 使用 `==`，弱持有 scope、token 和 value；固定容量、两种不同散列的候选槽及最近一次命中。主槽冲突时第二候选位置独立散列，降低三个 token 互相挤出的概率。碰撞只能造成 miss，不能决定内容不相等。
2. **L2 内容表**：使用自行实现的 `WeakOpenHashMap`，hash 相同后再比较原 `equals`；键、值都为弱引用。开放寻址查询接收 K 或临时 `Lookup<K, V>`；后者提供 hash 和对存储键／值的比较，不需要把查询对象保存在表里。
3. L1 miss 后查 L2；L2 miss 才调用 `key -> value` 工厂。并发候选在锁外构造，再原子选择已经发布且仍有效的实例。允许重复构造，调用者不应依赖工厂恰好执行一次。

创建函数和有效性检查不在缓存锁内运行；内容键须不可变，hash/equals 应保持稳定。清空使用换代，旧构造不能填入新一代。

开放寻址表的读取不加锁，数组槽使用 acquire/release 发布；写入、删除及扩容串行化，锁的范围限于同一个内容表。删除保留墓碑，避免截断碰撞后的探测链。扩容发布新数组，已取得旧数组的读者仍能完成查询。引用队列按节点身份删除，迟到的 GC 通知不能误删后来放入的等值实例；键或值先被回收均可清理。新值必须绑定自己的弱键，不能沿用已经失去所属 value 的旧弱键。

**若要求 value 活着期间一直保留其规范实例，value 必须持有传入的内容 key。** 若工厂丢掉这个 key，只保留等值副本，弱键可以提前被回收，这属于 API 允许的驱逐。AE2 适配器直接利用已有的 `AEItemKey → ItemStack → PatchedDataComponentMap → patch` 引用链：L2 弱键是实际规范 Key 所属的 patch，弱值就是 AEItemKey。查询探针只在本次调用中存在，不再添加 Entry／Fingerprint 反向持有字段。独立但等值的查询 patch 可以回收，不影响仍存活 Key 的规范实例。

强键弱值在 `K == V` 或 K 能到达 V 时，强键会把值也留住。双弱引用避免这种滞留；它与线程死锁是两类问题。已测试 K==V、K/V 互相引用、独立等值键、并发创建及清空期间创建。

GC 清空引用后，引用队列删除包装节点。热点内容访问执行有界清理；客户端／服务端 tick 每次最多检查 32 个注册 Item，每个内容表分别最多处理 32 个键队列和 32 个值队列节点。空闲期也能逐步清理，不在生产代码中强制 GC。L2 的规模随仍存活的规范内容增长，不再宣称整张表固定 4096 项。

## 组件适配

使用原生 PatchedDataComponentMap 的写时复制 patch 作为身份 token。组件变更分离 patch，新的身份不能误中旧内容。临时内容探针包含物品、prototype、patch 内容和原生构造保存的动态元数据；组件视图按原生不可变约定共享，没有额外深复制一份 NBT。

第一次复制新建可写组件继续旁路，避免为一次性对象计算整份内容 hash。重复转换或已有写时复制快照进入缓存：同一个 patch 命中 L1；独立但内容相同的快照可在 L2 汇合，再建立 L1 别名。工厂包装器在命中并验证后直接返回 key，不再重复走复制点和构造点查询。继承默认容量／耐久钩子的物品，在同一不可变 patch 和 prototype 下省去重复组件元数据计算；覆写钩子的物品仍逐次核对，包括带名称组件时动态变化的容量。不保存调用者的可变 ItemStack。

L1 别名弱保存规范 patch 的快照标记；与别名 token 相同时复用同一个弱引用。命中必须确认 Key 当前仍持有此快照，L2 也核对存储的弱 patch 与 Key 当前快照身份，避免非法修改只读栈后继续复用原生 hash／元数据已经过期的对象。

清空、旁路及不同的可观察栈状态仍可能得到不同实例，**不能因此把 AE2 equals 改成纯 `==`**。网络或存档解码的等值对象继续正常查库存。

## 为什么这里没有换 fastutil

检查了运行依赖 fastutil 8.5.12：`Reference*Map` 表示身份比较，不表示 GC 弱键；本次没有可直接替换的并发、内容相等、双弱引用表。若采用普通 Object2ObjectOpenHashMap，需要自行加入弱包装和并发保护。

使用同样的弱键包装、缓存内容 hash 和弱值，对 4096 个条目进行独立等值键读取，轮换后端测量顺序，3 轮预热、5 轮测量取中位数，每线程 400000 次，得到：

| 后端 | 单线程 ns/操作 | 4 线程总耗时÷总操作数，ns/操作 |
| --- | ---: | ---: |
| ConcurrentHashMap | 9.90 | 2.57 |
| fastutil，整表 synchronized | 12.19 | 57.57 |
| fastutil，16 个加锁分片 | 13.72 | 9.44 |

四线程列是吞吐量归一化，不是单个请求延迟。这是上一轮对预先构造好的弱包装键进行读取的基准，不包含完整规范化、写入及 GC 清理。当时因此保留了 ConcurrentHashMap；随后继续用自定义开放寻址表替换了 L2。

新的直接对照从原始内容 key 开始，包含上一版 CHM 每次查询构造弱键包装的开销，4096 个存活条目、独立等值查询 key，3 轮预热、5 轮中位数、每线程 400000 次：

| 后端 | 单线程 ns/操作 | 4 线程总耗时÷总操作数，ns/操作 | 查询分配 B/次 |
| --- | ---: | ---: | ---: |
| 原 CHM 弱包装查询 | 7.88 | 2.87 | 32 |
| 自定义弱开放寻址 | 5.42 | 1.57 | 0 |

保留了可运行的[独立基准源码](../scripts/benchmarks/WeakMapLookupBenchmark.java)。这仍是 L2 查询基准，不代表并发写入也更快；新表写入需要同表互斥，普通命中走无锁读取。Java 21 下可复现：

```sh
mkdir -p /tmp/tb-weak-map-bench
javac -d /tmp/tb-weak-map-bench \
  src/main/java/com/moakiee/thunderbolt/core/keys/WeakOpenHashMap.java \
  src/main/java/com/moakiee/thunderbolt/core/keys/WeakCanonicalMap.java \
  scripts/benchmarks/WeakMapLookupBenchmark.java
java -cp /tmp/tb-weak-map-bench com.moakiee.thunderbolt.core.keys.WeakMapLookupBenchmark
```

## 实际 AE2 运行结果

实际 NeoForge/AE2 Mixin 环境，未加入其他附属的独立进程，6 轮预热、7 轮测量中位数，每轮 200000 次，结果进入 volatile sink，分配量使用 ThreadMXBean。原始 Thunderbolt `3798e5b` 与本次版本使用相同外部比较程序、默认配置，顺序运行；绝对数值受 JIT、GC 和进程差异影响。

| 场景 | 原始 TB ns/次 | 本次 ns/次 | 原始 → 本次 B/次 |
| --- | ---: | ---: | ---: |
| 普通物品键 | 57.45 | 2.79 | 144 → 0 |
| 64 个普通物品 | 47.32 | 2.83 | 144 → 0 |
| 重复名称组件 | 78.48 | 31.26 | 288 → 0 |
| 重复复杂 NBT | 430.18 | 40.43 | 200 → 0 |
| 256 种组件轮换 | 78.97 | 58.60 | 288 → 0 |
| 独立等值组件转换后查询库存 | 1058.49 | 60.86 | 280 → 3.44 |
| 每次新建组件 | 107.92 | 113.84 | 624 → 632 |
| 普通流体 | 10.92 | 4.78 | 72 → 0 |
| 约 1700 种物品轮换 | 57.34 | 6.26 | 144.04 → 0 |

等值库存场景使用 256 份独立的等值 64 项 NBT 快照，预热后反复查已持有的规范键；它不代表每次新解码一份复杂 NBT 也只需要 61 ns。身份槽碰撞／GC 可带来少量额外分配；不同进程该场景测到约 48～62 ns。

与上一版实验 `caa258c` 相比，普通物品从约 30～33 ns、56 B 降到约 3 ns、0 B；组件 256 变体轮换则从约 40 ns 增加到约 59 ns，换来内容规范化及更少分配。每次新建组件新增约 8 B 的 AEItemKey 附加字段成本。不能把本次结果描述成所有负载都更快，也不能由微基准推算整包 TPS 或存量堆内存降幅。

### 前一版：Fast 记录直接挂到 Item

三次独立 JVM 拆测中，完整工厂中位数从旧结构的 2.160 / 2.332 / 2.327 ns 变为 2.084 / 1.782 / 1.813 ns，均零分配。该拆测使用独立循环体；原先通过工厂函数分发的完整场景基准仍约 3.5 ns，不能把变化宣称为固定节省 1.5 ns，亦没有测得整包收益。这是前一版结构的记录，当前版本进一步改为 Item 直接存 Key，见下节。

代价是所有 Item 对象都多两个引用槽，已创建 holder 则少两个引用槽；未使用缓存的 Item 也会承担前者。热路径不加锁，只有字段发布／拆除使用 Item 上的监视器。

删除 `PlainItemKeyCache.Fast`，保留 Item 上的两个 `volatile AEItemKey` 槽。比较过两种校验实现：直接读取 Key 的只读 ItemStack；以及把三个校验字段在构造时写入 Key 本身。最初保留后者；之后去掉重复的 count/popTime 字段，当前单件命中不再访问包装对象或 Key 内部的栈，其他数量／动画状态读取 Key 原有栈做校验。

前一版三个字段让新建组件场景从 632 B/op 增至 640 B/op，普通缓存命中仍为零分配。进一步以只读 Instrumentation 代理测量实际 Mixin 后的 AEItemKey，在本机 Java 21、压缩对象／类指针开启、8 字节对象对齐下，三字段版对象为 48 B。

这一历史版本删除了重复的 count、popTime 两个 int，只保留 prototype 引用，实测对象降为 40 B。单件槽的发布条件已经保证数量 1、动画 0；其他状态保留只读栈校验，不改变原有 Key 的数量／动画、动态物品钩子和组件模板语义。对象尺寸取决于 JVM 及其他附属加入的字段；40 B 是本次实测，不是通用 ABI 保证。单件拆测略快；本轮混合基准 64 件由 3.47 ns 到 3.88 ns，非单件读取原有栈有小幅代价，不能宣称所有路径同时加速。

## 32 B 试验：保留数据，恢复普通热路径字段

这一试验曾删除 `thunderbolt$plainPrototype` 与 `thunderbolt$componentEntry` 两个 Key 附加引用，也删除 `ComponentKeyOwner`。以下为 32 B 试验的测量记录；最终版本恢复前一个字段，结果见下一节。普通模板检查从已有只读栈读取；组件内容表使用 Key 已持有的 patch 作弱键，直接以 AEItemKey 作弱值。`ContentProbe` 仅是短期查询参数，原来的常驻 Entry 和 Fingerprint 均不再存在。L1 弱快照标记保留失效检查，未修改 AE2 原生 hash、equals、网络或存档定义。

在与上一轮相同的 Java 21、压缩引用、8 B 对齐环境，用 Instrumentation 测量真实 Mixin 后对象：**40 B → 32 B**。这是 Key 自身浅大小，不含 ItemStack、组件和缓存节点，也不代表整包堆内存下降 20%。普通路径保留 prototype 校验，兼容已有的自定义组件模板。

相同外部基准、每版三个独立 JVM 的中位数如下。40 B 为上一轮归一化版本；32 B 的混合基准已包含第二候选槽独立散列。独立循环与混合函数分发必须分别比较。

| 场景 | 40 B 版 ns/次 | 32 B 版 ns/次 | 32 B 版分配 B/次 |
| --- | ---: | ---: | ---: |
| 普通单件工厂，独立循环 | 1.048 | 1.529 | 0 |
| 普通 64 件工厂，独立循环 | 1.044 | 1.528 | 0 |
| 普通单件，混合基准 | 3.59 | 3.10 | 0 |
| 普通 64 件，混合基准 | 2.78 | 3.12 | 0 |
| 重复名称组件 | 10.00 | 11.33 | 0 |
| 重复复杂 NBT | 12.16 | 14.55 | 0 |
| 256 种组件轮换 | 21.37 | 20.53 | 0 |
| 独立等值组件查询库存 | 18.43 | 19.45 | 0 |
| 每次新建组件 | 124.11 | 120.74 | 648 |

普通工厂独立循环增加约 0.48 ns，换来移除 Key 的两个字段。名称组件本轮范围 8.66–11.40 ns，等值库存查询 17.88–20.00 ns。新建组件总分配量本轮 648 B/次，上一轮中位数 632 B/次；虽然 Key 本身缩小，整个调用的分配并未一起下降，不能混用浅大小与 JIT 逃逸分析影响下的总分配量。上述数据不证明所有路径变快，也不是 TPS 测试。

保留原先相同下标的两路槽时，本轮等值库存查询有两次退化到 35–37 ns、约 4 B/次；改为不同散列的第二候选槽后，三个 JVM 均恢复零分配。缓存仍有容量与碰撞边界，不能保证任意工作集永远命中。通用 L2 开放寻址另测为 5.81 ns/次、0 B/次，四线程总耗时归一化 1.83 ns/次；原 CHM 包装查询对应 8.26 / 2.92 ns、32 B/次。

本次完整 861 项 JUnit 通过，27 项真实 Mixin GameTest 在七附属共 807 种物品下通过；调整身份槽后另复跑 34 项缓存专项测试及全部 27 项 GameTest。新增五项单元测试和两项 GameTest，验证临时探针／源栈／独立身份别名回收后仍保持存活 Key 的规范实例，释放 Key 后其组件快照可回收，以及快照失效、并发创建、换代期间的晚返回。对象大小代理和外部基准不进入发布包。

## 最终采用：恢复 prototype 快照，保留直接弱引用

按热路径速度优先的要求，加回 `thunderbolt$plainPrototype`，构造完成后记录模板，普通命中直接核对该字段。Key 实测恢复 **40 B**；由于 8 B 对齐，一个 4 B 引用已经使 32 B 对象达到 40 B。组件 `Entry` 反向字段没有恢复，常驻 Entry／Fingerprint 继续移除，双弱引用和独立第二候选槽也保留。

| 普通单件，混合基准 | 3.10 | 3.60 | 0 |

最终普通单件独立循环范围 1.044–1.291 ns，64 件范围 1.060–1.166 ns。更早的双附加字段版单件范围 1.043–1.289 ns，与最终组合明显重叠；不能把跨进程约 0.1 ns 的中位数差断言为稳定退化。独立循环、混合分发的 JIT 情况不同，保留两类结果，不推断整包收益。新建组件分配总量仍未改善：这轮是 656 B/次，32 B 试验为 648 B/次，更早一轮为 632 B/次；组件常驻包装的减少与每次调用的瞬时分配是不同指标。

最终组合复跑 34 项缓存专项测试、27 项七附属 GameTest 全部通过；此前同一轮重构的完整 861 项 JUnit 也通过。正式实验 jar 不含 GameTest、外部基准或大小测量代理。该组合在对象复用实验分支维护，三方最终对照见后续测量报告。

## 验证与兼容边界

归一化版本完整 856 项 JUnit 回归通过，失败／错误／跳过均为 0，其中通用弱缓存 11 项、键构造缓存 11 项，新增开放寻址测试 7 项。新增测试覆盖冲突链删除、扩容、并发读写、弱键或弱值先消失及延迟队列事件。实际 Mixin 的 25 项 GameTest 全部通过；七个附属共 807 种物品参与联合运行，版本及更多覆盖见[对象复用实验](object-reuse-experiment.zh-CN.md)。新覆盖包括默认药水与空 patch、独立等值快照、带组件时的动态容量、数量／动画切换、旧 Item holder 拆除，以及旧构造器跨清空晚返回时不能覆盖新代 Key 字段；覆盖不同组件 prototype 的空 patch、8 线程交错切换数量／动画、构造器及网络归一化，以及数量相关的动态堆叠钩子。测试源集不进入发布 jar。

普通键与组件键的快路都在 AEItemKey.of(ItemStack) 工厂包装器中命中即返回，可能绕过其他附属在被包装工厂内部注入的副作用；不能宣称保留每次工厂 HEAD/RETURN 的全部执行。未命中的通用路径仍包裹复制／构造点。保留 AE2 原 equals/hash、组件内容和只读键约定；Key 内部数量／动画按用户要求归一化为 1／0，属于有意改变的可观察行为；若其他附属依赖每次工厂或构造副作用，可用 `reuseAeKeys=false` 禁用键复用。已验证七个具体附属版本，不能推导任意 Mixin 组合或整个客户端长期运行均被穷举验证。
