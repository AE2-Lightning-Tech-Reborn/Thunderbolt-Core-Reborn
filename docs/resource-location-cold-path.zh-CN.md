# ResourceLocation 冷路径优化

接续 [RL 缓存首次实现](resource-location-cache.zh-CN.md)，仍在对象复用实验分支，未合入 alpha。

## 修改

原来每个新 RL 都先查询内容表，构造后再查内容表，最后在写锁内复核；此外，同一个 RL 分别被弱键、弱值、快捷索引三个弱引用保存。首次完整解析还会立即创建组合字符串的弱别名索引和快捷别名。

1. 新增可复用的 `WeakCanonicalSet<V>`，用于键就是值的情况。表节点自身是唯一弱引用，4096 槽快捷索引复用同一节点。一般键值不同的 `WeakOpenHashMap` 保留原结构。
2. namespace/path 查询分别传入两个投影参数，取消临时 Pair。构造后直接进入有写锁的原子复核/插入，删除中间重复查询；原工厂仍在锁外执行。
3. 完整字符串索引改为再次观察到同一活 RL 时才建立。第一次就进入主表，身份规范化没有延后；延后的只是避免字符串拆分的第二层索引。记录这一提示使单弱节点为 40 B，因此专测两段式冷创建为 RL 24 B + 节点 40 B = 64 B。
4. 外层解析如果已经经过两段式工厂，通过查询直接取得规范对象，避免重复取得写锁。原有校验、值相等、hash 数值和配置代次隔离保持不变。

次级索引提示允许并发首次观察都返回“尚未见过”，仅延后加速索引的建立，不会产生两个活的规范实例。弱引用 GC、引用队列清理与数组扩容都不依赖这一提示。

## 同口径冷路径对照

新增 `ResourceLocationColdBenchmark`，每种实现三个独立 JVM，全部串行运行。每进程六轮预热、九轮测量，每场景每轮 20000 个全新 ID；输入字符串和输出数组在计时前创建。两种“保留”场景持有此前所有输出直到整轮基准结束，避免只测随用随丢的短命对象。

Minecraft 1.21.1 / NeoForge 21.1.219 / AE2 19.2.17 / Java 21.0.11 arm64；原始对象基线 `3798e5b`，Lean `22d4c093`。每格为 **ns/次；分配 B/次**，取三次进程中位数的中位数。

| 冷创建场景 | 原始对象基线 | Lean | 优化前 TB | 优化后 TB |
| --- | ---: | ---: | ---: | ---: |
| namespace/path，输出随用随丢 | 17.03；24 | 108.28；64 | 150.22；176 | **100.16；64** |
| namespace/path，持续保留输出 | 17.24；24 | 102.07；64 | 134.76；176 | **100.97；64** |
| 完整字符串解析，输出随用随丢 | 26.47；128 | 112.89；168 | 271.23；504 | **148.13；192** |
| 完整字符串解析，持续保留输出 | 26.95；128 | 111.07；168 | 289.01；504 | **150.85；192** |

两段式冷创建在本机这组专测中接近 Lean，完整解析仍比 Lean 贵。缓存首次创建也仍远贵于原版直接构造，不能描述成消除了冷插入成本。索引维护、写锁、弱引用登记、额外 hash 和校验路径仍需付费；本轮没有分别计时这些剩余因素，不能从源码推定各项耗时占比。

完整三次进程值、分配量、源码/日志指纹见 [冷路径原始数据](resource-location-cold-results.json)。使用现有 comparison harness 的 `-PcomparisonResourceColdOnly=true`，模式 BASE、LEAN、OURS_BEFORE、OURS_AFTER；配套 `summarize-resource-cold.py` 验证日志完整并汇总。

## 原有混合基准复核

另按原来的 `ResourceLocationBenchmark` 运行三个 JVM。其 JIT 上下文与上面的纯冷路径基准不同，不混填数字。

| 场景 | 上轮 TB ns/次；B/次 | 当前 TB ns/次；B/次 |
| --- | ---: | ---: |
| 新 ID 两段式创建 | 128.91；200 | 119.42；88 |
| 重复完整解析 | 3.72；0 | 5.37；0 |
| 重复 namespace/path 工厂 | 4.86；0 | 5.17；0 |
| 每次 new 等值字符串后解析 | 6.04；24 | 6.12；24 |
| 8192 个活 ID 轮换解析 | 11.78；0 | 10.91；0 |

原混合基准的冷创建耗时仅下降约 7%，分配量下降 56%；专测显示的 25%～48% 时间降幅不能套用到全部负载。当前两段式冷创建在两套基准中分别为 64/88 B，24 B 差额与工厂包装字节码中的临时 Object[] 大小相符，但未用分配栈将其最终归因。试过将原工厂调用移至各 Mixin 入口，额外分配并未消失，因此未保留该改动。

重复完整解析本轮约 4.62～5.53 ns，比上轮数字稍高；两段式热命中约 5.07～5.19 ns，大工作集约 9.60～11.04 ns。热路径仍保持对应零分配，未证明每项耗时都改善。实际整包收益还需命中率、总分配和 CPU/GC 采样。

## 验证

新增八项 `WeakCanonicalSet` 单测，覆盖快捷槽/内容 hash 碰撞、扩容、复用同一个弱节点、迟到 GC 通知、分批清理、垃圾回收、并发首次插入、并发读写与扩容删除，以及次级索引延后期间的规范性。原来的 GC GameTest 改为执行两次解析，确保确实建立次级索引后再验证回收。

**875 项 JUnit、36 项实际 Mixin GameTest、jar 构建通过**；GameTest 同时加载七个 AE 附属，覆盖 807 个物品和 12 种流体。源码指纹与测量版本核对一致。
