# Alpha 供应器候选调度优化（2026-10-22）

基线为 TB Reborn `alpha` 的 `69e9af1b35b533f4593c122eff7b46a3ee4c37cf`，Minecraft 1.21.1 / NeoForge 21.1.219。本文件记录供应器队列的优化和本轮组合验收；其他两项分别见[普通计划精确数量检测](exact-preview-hotpath.zh-CN.md)和[小额 BigInteger 存储接口](small-exact-transfer-optimization.zh-CN.md)。

## 调用位置与行为边界

AE2 与 AdvancedAE 的 CPU 批量执行 Mixin 都持有 `TickProviderDispatchSchedule`。稳定网络会跨 tick 复用候选快照，但每次重试仍遍历 `IdentityCandidateQueue`；原实现对遍历的每个节点重新查询身份哈希表。

- 候选节点从活动链移除后，其不再使用的前驱指针指向自身，表示失活；保留后继指针供正在运行的迭代器继续前进。遍历直接读取这个状态，恢复时重建活动链接，不新增节点字段。
- 成功优先项直接记录节点，迭代器仍捕获创建时的优先项。已有 `hasNext()` 缓冲的候选即使随后被屏蔽，下一次 `next()` 仍返回它，保持原行为。
- 失败映射和恢复列表在第一次屏蔽时分配。普通活动候选移除成功后，不再额外查询它是否已经屏蔽；未知候选、重复失败和 null 的失败记录仍保持原语义。
- 快照直接消费供应器 Iterable 并构建独立队列，去掉中间 ArrayList。完整扫描成功后才发布；网络对象、供应器修订、tick 失效规则及 4,096 个样板的 LRU 上限仍由原调度器维护。

没有改动候选优先顺序、共享催化剂归属、容量查询、能耗或原料结算。

## 基准方法

分别编译基线和修改后的 `IdentityCandidateQueue`、`TickProviderDispatchSchedule`，其余依赖相同。Java 21.0.12 / GraalVM，固定 512 MiB 堆；四个独立 JVM 按 A/B/B/A 运行。每场景预热 1.5 秒，采集 7 个至少 150 ms 的样本，下表为每个实现 14 个样本的中位数。计时期间不同时运行本轮其他重型基准或构建。

驱动调用真实队列及调度器候选入口，使用简单供应器和带修订号的来源。每个测量批次校验候选 ID 总和；失败/恢复场景还核对活动数、失败数，快照场景核对来源扫描次数。16 个场景共 448 个样本通过，源码和驱动哈希与最终文件一致。

这些数据只覆盖候选调度，不含机器执行、库存提取或服务器 TPS。空队列循环可被 JIT 大幅消除，不把亚纳秒结果作为有效收益。

## 正确性与复测

新增队列测试以普通列表和身份比较作独立模型，覆盖 5,000 步屏蔽/成功/恢复序列、500 组遍历中删除与优先项变化、同值不同实例、连续移除相邻节点、未知候选、null 和重复失败。调度器回归验证只能读取一次的来源、来源后续变化不影响快照，以及扫描异常后没有部分发布。已有的网络变更、LRU、跨 tick 恢复和批次实际分发测试一并执行。

存储集成时另加 10,000 次只使用 long 范围请求的混合 exact/legacy 操作，对照独立 BigInteger 账本，持续走小额路径；包含模拟、零数量、跨 63 位进位、两种键类型和 104 次增量保存/重载。原有大数边界与异步保存回归继续覆盖宽数值路径。

```sh
python3 scripts/runtime-hotpath-benchmark/run.py --suite provider-schedule \
  --baseline-ref 69e9af1 --warmup-ms 1500 --sample-ms 150
./gradlew --offline -I scripts/benchmarks/cell-stress.init.gradle cleanTest build
```

原始样本位于 `build/provider-schedule-benchmark/`，不提交本机日志。两个协作报告中的构建数量及存储 JAR 哈希属于各自独立验证；组合版本的验收以本报告为准。

## 组合验收

三处优化组合后，执行上述 `cleanTest build` 成功：181 个测试套件、1,419 项测试，其中 1,414 项通过，0 失败、0 错误，5 项因可选模组或所需 API 未提供而跳过。跳过范围为 ExtendedAE Plus 1 项、NeoEco 3 项、Useless 1 项，与基线一致。

存储守恒压力测试执行 4 个种子各 250,000 次操作，共 1,000,000 次，覆盖 3 个元件、1,024 个键和 372 次重载；异步保存测试覆盖 16,384 个键、12 代数据与 24 次有序写入。新增的小额 exact 路径对照另完成 10,000 次操作和 104 次增量重载。

三组基准的生产源码和驱动哈希均与最终整合文件一致。构建 JAR 中四个修改过的生产类与测试使用的编译类逐字节一致，测试和基准驱动未进入 JAR。组合构建 `thunderbolt-2.0.3-beta3.jar` 的 SHA-256 为 `cb30ef450799639af22a2217fff15fe4b0d067826a8c59ebbe543369d7f15dcd`。

性能边界仍需保留：单候选纯遍历约多 0.11 ns；旧 long 存储接口在混合矩阵中约慢 7%，独立加长预热复测未复现，因此不承诺全部工作负载均无回退，也不把这些离线数字换算为服务器 TPS。
