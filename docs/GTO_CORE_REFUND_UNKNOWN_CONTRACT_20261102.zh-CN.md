## 最小 LT 状态与唯一责任

设调用前确定持有量为 `R`，本次实际传给接收端的量为 `S`。
exact 接口中 `S=R`；当前 `.5` legacy 桥中 `S=min(R, Long.MAX_VALUE)`，只调用一次，
不是按数量循环转移。`R-S` 是未尝试的确定尾量。LT 可保守冻结更大的已知余额，
但必须区分已知余额和本次不确定敞口。

在调用外部 MODULATE 之前，为该尝试登记意图，将 `S` 从可花费/可退款/可物化
escrow 中排除，保留完整 AEKey、精确数量及关联身份，并确保 dirty/save 覆盖该状态。
状态名和字段名由 LT 自行实现，以下是行为要求：

| 状态与事件 | 必须保留的行为 |
| --- | --- |
| READY → INVOKING | 先登记尝试与隔离量，再调用接收端；避免同步重入看到全额可退款余额 |
| 正常合法回执 `A`，`0<=A<=S` | insert 的 `A` 是已接收量；仅将 `S-A` 释放回确定余额，最终已知 escrow 为 `R-A`；这一次尝试只结算一次 |
| 正常 `A=0` 或部分接收 | 保留真实未接收余额及其唯一保管者，后续可用新尝试退款；不得重复包含已接收部分 |
| 异常、无/非法回执、接受状态不明 | INVOKING → UNKNOWN；不得按 0、全额失败或回滚处理，不自动重提、补偿提取或转换为普通回退 |
| 保存中或恢复到 INVOKING | 缺少已完成回执时按 UNKNOWN 保守恢复，不能回到 READY |
| UNKNOWN 后的 tick/取消/恢复/重连 | 保持隔离及原尝试身份，不清除状态或再次调用外部 insert |
| UNKNOWN 的权威对账 | 只有与该尝试匹配、能确定接收量或明确无副作用的证据才可结算；在正常 tick 中不猜测接受量 |

一次 UNKNOWN 至少需要可恢复的 job UUID、尝试标识、完整键、`S`、已知尾量/来源关系、
状态及目的库存可用的定位信息。涉及组/种子的原有身份一并保留。没有稳定目的 ID
时保留可用定位信息并保持未确定，不因出现新的 IGrid 对象而重试。
本地 UUID 仅用于关联；接收端未承诺去重时，重用 UUID 仍不是安全重试。

隔离记录中的 `S` 是本次**接收量未知的敞口**，不是另一份实际物料。当前案例中，
接收端确实有 2，正确行为是停止再次回存并保存 UNKNOWN；不能同时把记录的 10
加到可用库存，也不能无回执地声称恰好还持有 8、已经全额退款或已经完成订单。
真实拆分只有故障夹具/权威回执知道，对账责任由 LT 唯一保留，不冒充物理全额保管。

## LT 必须配套的边界

1. `returnEscrow` 的意图登记、正常回执结算与 UNKNOWN 隔离；循环异常不能留下仍可
   自动退款的全额记录。必须在异常路径也使状态可保存，而不只是打印异常或改状态文字。
2. `BigCraftingJob` 的独立持久状态及 save/load；单独设置 suspended/dispatchFailed
   不足以阻止当前 returning 分支。取消不得抹掉未知记录；恢复不得重置成可退款状态。
3. job/CPU 完成、取消完成、清理及成功回调必须同时确认没有 INVOKING/UNKNOWN。
   移出 active escrow 后即使 escrow 为空，也不能触发当前 `job=null` 而丢掉对账责任。
4. UI、库存快照、再次规划/合成、取消回收、拆除掉落及转存不能把隔离敞口作为物品。
   owner 迁移必须是一次持久责任转交；不能复制记录后使两个服务都能结算。
   若拆除路径不能把原记录转交给唯一、可恢复且不产生物料余额的 owner，就必须阻止
   或延迟该次清理/删除。本步未读取 controller/拆除源码，由 LT 核查这些授权内路径。
5. 在正常存档兼容范围保留旧格式支持；新 UNKNOWN/未完成意图的状态或字段不能丢失
   后回落为 READY。无效记录应保留隔离和诊断。缺少历史意图的旧存档无法仅凭原
   escrow 数量恢复过去的实际接收量，不能宣称自动修复既往未知转移。

当前缺口的有序 save/load、退出保存与三 JVM 恢复可以在现有接口下验证。
`markCpuDirty` 或调用 `save()` 产生 NBT 不等于已在调用外部前持久落盘：若要宣称
任意进程崩溃也不会重放，必须证明接收端生效前已有可恢复的意图记录，或另有双方
事务/幂等保证。普通异步 NBT 保存不能代替这个证明；此限制不能被“跨 JVM 通过”掩盖。

## 什么时候才需要最小共享契约

本轮“持久隔离、停止重放、等待对账”不需要新 Core API。若以后要求在无回执后
自动完成退款或跨模组恢复，则需要接收端参与的契约：稳定转移 ID 及 source/destination
scope、完整键和精确 offer；接收端把实际效果与去重/回执持久关联，同一 ID 重放
不会增加效果；可查询或重取已确定的接收量，或明确保证该尝试无副作用。
无法确定时必须仍能表达 UNKNOWN，不能把“没查到”直接解释为零接收。

只新增一个返回结构、调用方 UUID 或包装任意异常，无法从既有非幂等 `MEStorage`
推导出丢失的接收量。库存前后差值可能含并发变化，也不能替代匹配的操作回执。
若确需此类跨项目协议，再回①集中定义、由接收端实际实现并重新冻结/验证；本次
不新增这些方法或改变固定 `.5` 坐标。

## A6 修复验收交回条件

LT 继续其他独立验收，本缺口至少需以下实际行为证据，再由 LT 给通过结论：

- 真实故障接收器已接收 2 后抛异常；经过重复 tick、NBT 恢复及取消，外部调用不再
  重放（记录调用数且实际余额仍为 2），未确定记录和 job/attempt/全键/数量保持。
  仅断言 `stored<=10` 不足以证明没有吞掉记录或猜测接受量。
- 已知 escrow/可用库存/合成输入/掉落数量不包含隔离敞口；未确定记录不会被完成清理
  或拆除物化。若转交 owner，证明只有一方保留处置权且恢复后仍成立。
- 零回执和部分回执仍有守恒控制：0 接收保留 10，接收 3 保留 7；保存恢复后仅退款
  真实余量，外部最终为 10。补充精确量/legacy 投影边界时区分 `R-S` 已知尾量。
- 真实保存退出/恢复覆盖未确定意图与隔离状态；三独立 JVM 检查不能被同进程 NBT
  重建替代。异常经 `h.fail` 记录，保留初始崩溃与后续规范失败，勿放宽数量和预算。

LT 若修改 BigCraftingService/Job 或持久格式，需按新 LT 字节重跑受影响的 A6、A8
及 exact/取消/清理路径；其他确实独立的 Core/ABI 结果保留各自输入身份。固定 Core
`.5` 的既有通过项不被本文件重标为外部退款通过，第⑨步仍等待 LT 实际结论。
