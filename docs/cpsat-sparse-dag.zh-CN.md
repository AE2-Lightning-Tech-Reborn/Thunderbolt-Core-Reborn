# CP-SAT 普通依赖图的稀疏表示

原排名模型在 Java 侧创建五张 `配方数 × 物料数` 的 long 矩阵，桥接建模还会遍历零元素。10,000 配方且约 10,000 物料时，仅这五张表就约 4 GB，即使真正的配方输入输出关系只有几万条，也会在 768 MB Java 堆下耗尽内存。

`CpSatSparseDag` 对普通无环主产物依赖图改用稀疏编译：只保存实际输入、输出及每种物料关联的配方，不创建二维稠密表。整个目标依赖图仍作为一个 CP-SAT 模型求解，没有拆分库存或分别求解组件。

## 范围及语义

- 当目标依赖图的 `配方数 × 物料数 ≥ 1,000,000` 时尝试稀疏表示。该阈值只决定表示方式，不是规模上限；小图保留原有搜索行为。
- 当前适用于所有候选配方合起来也是 DAG 的普通配方，支持多路线、任意正整数批量、共享库存、重复输入槽及缺料。副产物、环、返还物、有限耐久及私有种子保持现有排名模型，此次没有解决这些模型的大规模稠密内存问题。
- 整个目标图先做线性复杂度拓扑核验，再把稀疏物料行传到隔离的原生运行时。无需为已经证明无环的图创建排名变量；缺少虚拟排名不会放宽执行顺序。
- 保留原排名模型的缺料、配方执行次数、库存消耗优化顺序；保留主产物需求约束及末批余量，不能凭副产物或多余产物增加执行次数。沿用原有 long 安全变量域；数值域受限而没有候选时不提升为数学无解证明。
- 新模型仍允许缺料的物品仅为天然原料。固定为零的中间品缺料变量无需逐层优化，避免长链缺料时每层重复调用原生求解器。
- 编译、建模及原生搜索共享调用期限，仍预留剩余时间的四分之一供结果校验。桥接内部的建模时间也计入传入预算。
- 原生结果须经过原始图上的 BigInteger 物料平衡、主产物需求和 DAG 任意可执行顺序校验；缺料由原始库存重新计算，不能直接信任原生输出。

## 无关配方筛选

原有代码已经在两层按目标筛选：

1. `FastCraftingPlanner.buildGraph` 从目标物品入队，只查询该物品的候选配方，并递归加入其输入及相关返还物。
2. `CpSatRankedFlowSolver.compile` 再从目标沿候选配方输入遍历，只有可达配方和物料进入模型。

稀疏编译保留同样的目标闭包，表示方式的规模判断也只计算这个闭包。新增回归在仅需一条配方的目标旁放入 10,000 条无关的自循环、副产物配方，证明它们既不扩大目标模型，也不影响 DAG 准入。仍须保留目标依赖中相关的备选路线，不能为了减小模型而误删可行或更省原料的路线。

## 验证

在原来的 768 MB 堆预算下，10,000 配方链及约 10,000 配方宽图从编译阶段内存不足变为约 0.24、0.26 秒解出。进一步限制为 128 MB Java 堆，两种图分别以请求量 1 和 10¹² 复测，四次均可行，约 0.27～0.31 秒。计时不包含首次原生库加载，Java 堆限制不代表整个进程的内存上限。

测试包括万配方链、万分支宽图、万亿请求的一单位原料短缺及补料重算、10,000 条无关配方隔离、100 张随机 DAG 与原排名模型的缺料/执行次数/库存目标对照、重复配方身份、特殊语义回退及取消传播。

这些数据证明此次普通 DAG 表示的内存瓶颈得到修复，不保证任意组合图都能在 3 秒内找到最优解，也不代表复杂环或状态模型已经稀疏化。
