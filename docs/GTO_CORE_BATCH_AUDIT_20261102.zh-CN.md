## 共享种子的重复退款

旧 `reinject` 在 `remainingCopies == 0` 时仍继续执行共享输入退款。此时普通输入的
返还份数为零，但 `reinjectShared` 又向库存写入一次种子。

复现固定一份共享种子、32 份普通材料，每次合成消耗两份普通材料，取八份合成输入。
先后退四份、四份后库存恢复为一份种子和 32 份材料；再用旧剩余数量调用退款，种子
错误增加到两份。原生及旧兼容取料重载均复现。修复在实际可退份数为零时立即返回，
保持部分退款期间由剩余批次保管种子，最后一次退款才转回库存。

新增两项参数化回归逐阶段核对库存与批次保管的实际数量、剩余份数及重复退款幂等性。
最初夹具把 KeyCounter 的 `isEmpty` 当作零数量，先触发了夹具失败；AE2 可能保留
零数量条目，因此改为核对实际数量，再在未修复实现上复现 **1 → 2**。夹具失败、
产品失败及修复后通过原件分别保留，没有把首轮夹具失败计为缺陷复现。

| 验证 | 实际结果 |
| --- | --- |
| 正确夹具 + 旧实现 | **2/2 预期失败**，共享种子从 1 份变为 2 份 |
| 修复后批量专项 | **94/94 通过**，零失败/错误/跳过 |
| 修复后完整 JUnit | **1,688 项：1,686 通过、2 跳过、零失败/错误** |
| 冻结共享文件 | **82 个无改动** |
| 两版真实 AE2 JAR 输入及开发映射 ABI | `.31` **14/14**、`.40` **14/14** 通过，分别冻结原件及映射副本哈希 |

两版原件 SHA-256 分别为 `f63917bf5a2ca0692c0550ad2d045991f7a493d89021bfb30b51026d4ad31a3d`
和 `b0d97544e618d73ec0c8d8e54df36351bf7f98f7e1984c6455d81658b6320b5c`。
运行的是现有 `ae2AbiTest` 与各自 official_1.20.1 映射副本，结果逐轮归档，
不等同于最终完整重混淆 Core JAR 在正式加载器中的行为验收。

两项 JUnit 跳过仍为缺少可选 EAEP SuperMatrix/Useless 的真实接口输入。
已有专项同时覆盖模拟、准入失败、完全/部分拒收、取料不足、共享输入与输出、费用结算、
未知提交停止和 provider/cache 生命周期；本次没有改写这些结算路径。

`ListCraftingInventory.insert` 是承诺写入的内部 void 方法，不提供外部库存拒收回执。

## before/after 测量与限制

复用既有 `optimizationBenchmark` 和 `batchAllocationBenchmark` 的场景、库存、合成数量、
迭代次数及预热次数。增加的只有各场景预热前一次调用、20 个原始测量样本、分配量、
冷/预热/测量 GC 计数和时间、实际实现 class 的 SHA-256 与载入来源。

before 使用固定 `.4` 正式原包经 ForgeGradle `RenameJarSrg2Mcp` 转为 official_1.20.1 的
开发映射副本，并放在当前 main 类目录之前；after 使用本轮编译类。每轮检查实际载入
来源及哈希，不用 classpath 顺序本身证明对照。原包及副本哈希分别记录；映射副本仅作
基准输入，不能作为正式原包在 Forge 的运行证明。

同一机器、Microsoft Java 21.0.10、G1、`-Xms512m -Xmx1024m`、同一套依赖、测量入口
和测试 agent。两个入口分别运行 before/after 各三个独立 JVM，共 **12 个 JVM**，
串行执行，第二轮反转前后顺序。发现预热过渡信号后，保持生产实现及输入不变，另对
批量入口加 `-Xbatch`，两侧再各三个 JVM，共 **6 个诊断 JVM**。两组独立报告，不混合。

下表为每组各三个 JVM 的 p50 中位数；变化为 after/before−1，正数表示该轮耗时增加。
默认编译组保留原始信号，不用诊断组覆盖它。

| 批量场景 | 默认编译 before → after（ns/op） | 变化 | `-Xbatch` before → after（ns/op） | 变化 |
| --- | --- | --- | --- | --- |
| 原生单槽 | 694.8 → 732.9 | +5.5% | 257.5 → 261.6 | +1.6% |
| 原生九重复槽 | 2,324.7 → 6,033.9 | +159.6% | 1,720.0 → 1,618.2 | −5.9% |
| 原生九不同槽 | 2,353.6 → 2,386.1 | +1.4% | 2,631.7 → 2,849.4 | +8.3% |
| 原生保留库存 | 2,470.1 → 2,549.7 | +3.2% | 2,578.4 → 2,967.9 | +15.1% |
| 原生共享种子 | 2,529.6 → 2,613.0 | +3.3% | 2,694.9 → 2,991.1 | +11.0% |

默认组的重复槽原始样本在单个 JVM 内可从约 6,000 ns 降至约 1,500 ns；before 和
after 都出现过该切换。同步编译对照未复现同样倍数差异，说明默认组受编译阶段影响，
不能据其三次中位数断言稳定的 2.6 倍退化。其他场景仍有耗时上升，尤其同步组保留库存
为 +15.1%，这些信号留给审查评估，不宣称“没有性能回退”。同步组七个场景的分配量
before/after 均相同；本步未做性能优化，也没有可交付的提速比例。

优化入口七个场景的原始样本同样保留在数据中，p50 中位数变化为 −22.8% 至 +32.1%，
不把这种混合结果解释成算法提速。冷计时明确指场景预热前第一次调用：只有首场景
处于新 JVM 冷态，后续场景已经共享类加载/JIT 状态，不能宣称每场景都经过独立冷启动。
部分主机 CPU 百分比读数不可用；记录 Java 进程数和可用内存，但未严格控制全部后台
负载。结果是带限制的实测证据，尚不支持稳定性能优劣结论。
