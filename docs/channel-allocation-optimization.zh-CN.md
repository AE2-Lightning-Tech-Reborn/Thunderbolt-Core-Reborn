# 频道分配：双向树上批量配对与精确残量求解

下表保留 1.21.1 NeoForge `alpha` 的历史测量，以 `3242dc07fe209cc1164f25c7aac4251625ef4ef6` 为基线；这些数字不是 Forge 1.20.1 的实测结果。

Forge 1.20.1 的 JDK 17 快速复测以 `49233dceba0f0d34b0b7baf78e66b41fc42d3138` 为基线：1000 个随机图、并行路径和断开重连检查全部通过。小树状图中位数从 0.805 ms 降至 0.537 ms，1000 需求梳状图从 156.145 ms 降至 0.886 ms，20000 节点长链从 15.289 ms 降至 6.567 ms。原始结果由 `--quick --oracle 1000` 写入 `build/channel-benchmark/results.json`；它们是本机一次快速测量，不代表完整大型场景。

## 算法

完整保留原图中的拆点容量、双向连接、每块高容量控制器供给、原版控制器每面供给、无线限额、终端请求以及多方块代表节点。

1. **同容量优先建树。** 在原图上建立生成森林，先遍历相邻、容量相同且连接容量足够的节点，再处理区域边界。每个真实节点都保留；未选为树边的连接仍保留在残量图里。同容量只影响访问顺序，不代表整个区域的吞吐量。
2. **双向批量配对。** 自底向上汇总子树剩余供给和需求，在汇合处配对，并保留节点及父连接的剩余通过能力。随后自顶向下确定实际用量，写入原来的拆点边、物理连接、供给边和消费边。单次遍历可以处理不同深度的需求，无须为每个频道从源重新走完整路径。
3. **精确补齐。** 如果还存在未用供给与未满足需求，最多进行四轮残量生成树批量增广；仍未完成时使用最高标签推送—重标号。反向残量允许撤销先前的选择、改走另一条并行路。停止条件是达到供需上限，或不存在残量源汇路径。
4. **清除同一连接的相向循环。** 同时存在 A→B 和 B→A 的流时，抵消较小值，并同步扣回 A、B 的拆点流量，再生成 AE2 读取的结果。

因此，“双路各 8”保留两条独立路径，能提供 16；“双路共用一个 8 中继”仍受该节点容量约束，只能提供 8。生成树只是初始可行分配，不能单独作为整个有环网络的最终答案。

本实现采用树上供需配对作为区域初始分配，接精确残量求解；不是论文中的完整 ARD 区域标签算法，也未引入区域压缩或仅按设备数切换算法。

## 为什么初始分配不会透支容量

对节点 v，底向上收到的可用供给、需求分别为 S、D，节点容量为 C。在该节点配对 M ≤ min(S,D,C)，向父节点最多导出 `min(abs(S-D), C-M, 父连接容量)`，只导出一种方向的未配对数量。

自顶向下，父节点可取用的导出量 F 不超过上述上限。节点拆点流量恰为 `M + abs(F)`，所以不超过 C；每个子节点只承担自己承诺过的数量。根节点的导出量设为零。因此每个普通顶点都守恒，源、汇的净流量相等，且配对总数等于实际送达需求的数量。中间累计使用 long，避免许多大容量供给或需求相加溢出。

后续增广只修改真实残量边。推送阶段将送不到汇的余量完整退回源；只有所有中间 excess 为零才返回。初始可行流与后续残量可行流相加，仍是原图的可行流。它们共同达到上限或最小割时才完成分配。

树上两遍处理及每轮残量树处理均为 O(V+E)。一般复杂网络仍可能进入推送—重标号阶段，不能宣称任意拓扑都在线性时间完成。所有深路径处理均使用数组，消除了原递归 DFS 的栈深限制。

## 建图及结果映射

- 节点一次编号并拍摄容量快照；读取结果时沿数组取回，不再重复查询容量和节点编号。
- 每个双向 `GridConnection` 仅从编号较小的一侧建图，保留不同的并行连接，减少连接去重哈希集合。
- 结果映射按已知节点/连接规模预分配；推送阶段的标签、活动桶、excess 等数组按需分配。
- `Result`、设备回调和现有 Mixin 回写入口不变。供给不足时仍最大化总频道流量；获配设备或具体路由可能改变，不保证最大化足额获配设备数量。

## 正确性验证

- 全仓库 Gradle 测试与构建通过：809 个测试，0 失败、0 错误、0 跳过。
- 新增纯算法测试：3000 个随机物理网络、2000 个随机有向残量网络，独立矩阵 Edmonds–Karp 对照；检查每条边的容量、每个中间顶点的守恒、源汇总量及最大流/最小割证书。初始分配也单独检查可行性，推送内核有强制执行覆盖。
- 实际 AE2 `GridNode` / `GridConnection` 夹具：20000 个随机图对照，单路 8、双路 16、共享瓶颈 8；无线限额、物理连接、多方块、不可转发、无限模式、反复变更控制器容量均通过。
- 拆除一路后从 16 降至 8，再接回恢复 16；旧连接在新结果中不残留。8/32/128 同容量路径均有覆盖。
- 20000 节长链在 `-Xss1m` 下通过；旧版同配置栈溢出。另有 20000 节梳状树的纯内核守恒验证。

测试会验证最终流量可行性；相向循环清理只针对同一物理连接形成的四边闭环，不声称已经移除了任意长度的所有环流。

## 压测方法及边界

相同机器、JDK 21、G1、`-Xss1m -Xms512m -Xmx2g`，旧版和新版分开启动 JVM 串行运行。大型场景先冷启动一次、额外预热 3 次，再采样 7 次；小场景使用更多预热与采样。表中为完整 `assignChannels` 的中位数，包含发现、建图、求流与结果映射，排除夹具构造和断言。

夹具使用真实 AE2 类与人工拓扑，13.6 万设备场景为 266 个高容量源、X4 模式、总供给 136192。控制器按图结构连接，不是 Minecraft 世界内合法多方块摆放的证明；有限容量环网入口每处只有 128，总实际分配应为 34048。结果不包含整合包里的完整 Mixin 应用、设备激活、世界加载、功耗或服务器整 tick 耗时，不能直接当作 TPS 数据。

## 复现

在 Forge 1.20.1 工作区设置 JDK 17 的 `JAVA_HOME`，然后执行：

```sh
./gradlew --offline test build
python3 scripts/channel-benchmark/run.py --offline --oracle 20000
```

首次获取依赖时去掉 `--offline`。`--quick` 只运行小树、梳状网和长链；默认 `--oracle 5000`。脚本用 `git show` 导出指定基线到 build 目录，不修改原工作区；可用 `--baseline <commit>` 指定基线。
