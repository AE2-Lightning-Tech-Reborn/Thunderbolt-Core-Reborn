后续普通流体与 NBT 优化见[本轮复测报告](object-reuse-fluid-nbt.zh-CN.md)；本文保留原测量版本和历史数据。

2026-09-19 实测。实现已提交为 `2c9fd75`；以下数字对应这一固定实现，不把历史 32 B 试验或旧轮次结果混入本表。

## 版本与测量方法

| 模式 | 固定版本 | 含义 |
| --- | --- | --- |
| 原始基线 | TB [`3798e5b`](https://github.com/AE2-Lightning-Tech-Reborn/Thunderbolt-Core-Reborn/commit/3798e5b0300eddb19706cd9352ba0a29f957048b) | 对象优化之前的 AE2 原生对象实现；仍有 TB 其余功能，不是彻底移除 TB 的整包 |
| Lean 最新 | [`22d4c09`](https://github.com/nutant233/Lean-Object/commit/22d4c0930353b4904a75499f47f25d876e26b2ef)，`neoforge/1.21.1` | 本轮重新 fetch 和 ls-remote 核实的分支最新提交，原始源码无修改，加载在同一原始基线中 |
| 当前 TB | [`2c9fd75`](https://github.com/AE2-Lightning-Tech-Reborn/Thunderbolt-Core-Reborn/commit/2c9fd7581495e42414c4ba18182f4eb74fc94f97) | `experiment/object-reuse-20260919`，保留普通 prototype 快照和直接弱组件缓存，不加载 Lean |

三方共同使用 Minecraft 1.21.1、NeoForge 21.1.219、AE2 19.2.17、Temurin 21.0.11+10、arm64。Lean 原项目配置 NeoForge 21.1.234，为统一环境以 `-Pneo_version=21.1.219` 构建。基线目录的 390 个受版本控制文件逐一与原始提交核对一致。Lean 使用默认开启配置；TB 使用默认配置，ResourceLocation 构造复用默认关闭。

每种模式各跑三个独立 JVM，按 BASE→LEAN→OURS、LEAN→OURS→BASE、OURS→BASE→LEAN 轮换，顺序执行避免争用 CPU。独立工厂循环和混合基准分别启动进程，总计 18 次计时运行；大小测量另开三个进程。所有计时运行都完成相同的外部 GameTest 宿主。

结果写入 volatile sink。独立循环为 8 轮预热、9 轮测量、每轮 100 万次；混合分发为 6 轮预热、7 轮测量、工厂每轮 20 万次、NBT 每轮 5000 次。表中取每 JVM 中位数，再取三个 JVM 的中位数。`B/次` 为 ThreadMXBean 当前线程总分配；不包含其他线程，不等同于存量堆占用。

每格为 **ns/次；B/次**。独立循环和下一节混合分发有不同 JIT 上下文，应在各自表内比较。

| 场景 | 原始基线 | Lean 最新 | 当前 TB |
| --- | ---: | ---: | ---: |
| 普通单件 | 43.41；144.00 | 0.83；0.00 | 1.04；0.00 |
| 普通 64 件 | 43.66；144.00 | 0.84；0.00 | 1.04；0.00 |

单件三个 JVM 范围：BASE 42.324–44.353 ns；LEAN 0.826–1.036 ns；OURS 0.999–1.044 ns。普通命中 Lean 领先约 0.22 ns；两种优化均零分配。

| 64 子项 ListTag 复制 | 3259.83；18944.01 | 898.63；12112.01 | 1329.49；13672.01 |

重复组件是当前 TB 的主要优势：名称约为 Lean 的 3.6 倍速度，复杂 NBT 约 9.1 倍，等值库存查询约 30.2 倍；这些是热工作集微基准比值。普通单件混合分发结果几乎相同，不与独立循环交叉取数。

不占优的场景也保留：新建组件当前 TB 相对原始基线约慢 6.3%，分配 656 对 624 B/次；Lean 在普通流体、重复 ResourceLocation、ListTag 复制中更快。CompoundTag 复制耗时当前 TB 略低，但 Lean 分配量更少。不能概括成全负载优于 Lean 或原版。

波动与边界：

- 等值库存场景三方均查表命中 256/256。输入为 256 份已建立的独立等值 64 项 NBT，测的是预热后的重复转换与查询，不含每次新解码 NBT 的成本。
- 名称、路径等工作集会跨轮重复，不是无限不重复输入。缓存驱逐、GC、C2 内联和逃逸分析会影响分配量；例如当前流体分配范围 0–24 B/次，ListTag 为 8000.01–13672.01 B/次，不能把中位数当作固定对象尺寸。
- Lean 新建组件分配中位数为 549.22 B/次，完整范围在 JSON；它与 Key 的浅大小不是同一指标。
- 物品轮换的测试注册项不同：BASE/LEAN 1699 种，OURS 1701 种，原始测量保留于 JSON，不以此作严格排名。
- 未做 TPS、客户端渲染、长期整包负载或全堆留存分析。当前 default ResourceLocation 构造复用关闭，比较的是各自默认策略。

## 对象大小与语义检查

| 检查 | 原始基线 | Lean 最新 | 当前 TB |
| --- | --- | --- | --- |
| AEItemKey 自身浅大小 | 32 B | 32 B | 40 B |
| 空物品 ItemLike 工厂 | 返回 null | 抛 `stack is empty` | 返回 null |
| 原始空 patch 药水匹配输入 | 正确 | 不匹配 | 正确 |
| 默认药水存档／网络往返相等 | 正确 | 不相等 | 正确 |
| 解码药水键查原库存 | 命中 | 未命中 | 命中 |
| 强制并发首次构造后两个同值键相等 | 是 | 否 | 是 |
| 上述两个键放入 HashMap 后类型数 | 1 | 2 | 1 |
| 动态堆叠上限 64→16 后再次构造 | 16 | 仍为 64 | 16 |
| 输入 count=64、popTime=5 的 Key 内部栈 | 64、5 | 1、0 | 1、0 |
| 注册物品扫描：输入不匹配数 | 0 | 4 | 0 |

三轮语义探针观察一致。Lean 不匹配的四种物品为 potion、splash_potion、tipped_arrow、lingering_potion。以上是固定提交和配置下的复现结果，不推断其他版本或全部附属组合。`ComparisonProbe` 的宿主通过只表示审计执行完成；语义差异来自逐项观察，不能用 Gradle 成功覆盖这些异常。

Key 内部归一化是已接受的策略差异，原始基线保留 64、5 不算错误。当前 TB 保留原有值相等/hash、动态元数据与模板检查。40 B 包括用于普通快路的 prototype 引用，不再附加组件 Entry 反向引用。对象大小单独用 Instrumentation 测量，启用压缩引用、8 B 对齐；不包含 ItemStack、组件或缓存节点。

当前实现另通过完整 **861 项 JUnit** 和七附属联合的 **27 项真实 Mixin GameTest**，涉及 807 种附属物品；版本和覆盖见[对象复用实验](object-reuse-experiment.zh-CN.md)。性能进程不加载这七个附属，不能把本表当作全整包兼容证明。
