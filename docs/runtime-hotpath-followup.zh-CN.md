# 第二轮性能优化：大整数执行证明与批量分发

本报告记录 TB Reborn `main` 开发阶段结果，基线为本地提交 `591bfba`，Minecraft 1.21.1。本轮仅修改 `BigExecutionProgram`、`SharedBatchInputs`、`BatchExecutor`，当时保留工作区已有的规划器和版本文档改动。后续 `alpha` 整合单独记录于文末。

## 改动与行为边界

1. **大整数执行证明**：一次 `certify` 内按 `CraftPattern` 实例缓存不可变的物料消耗／产出摘要，初始容量受原有工作上限约束；直接迭代待执行表并移除已完成项，避免每轮复制；复用已计算的步骤摘要生成重复块。缓存不跨调用，不包含库存、剩余次数或决策。最终仍调用 `of` 从真实配方独立重建全部证明，未降低 200,000 次扫描上限，也未把拒绝认证解释为不可合成。
2. **共享输入扫描**：`hasSharedInputs` 在本次扫描内使用已经取得的输入槽对象，避免每个候选材料再次调用 `getInputs()`。`PlannedInputPattern` 的防御性数组复制由“每个候选复制一次”降为“一次扫描复制一次”。显式共享标记、完整 AEKey 相等判断、后续调用读取最新输入的行为不变。
3. **共享供应器选择**：共享催化剂只允许投给一个供应器，因此将全量排序后取第一项改为线性查找。保持 UNBOUNDED 优先、同组容量大者优先、并列保留最先出现者。普通分发仍按原顺序排序，复用无状态比较器，并在求总容量时同时检查 UNBOUNDED 标记。复制预算、能耗、原料扣取和异常归属处理不变。

## 测量方法

分别编译基线和优化后的真实生产类，以相同依赖执行 A/B/B/A 四个独立 Java 21.0.12 / GraalVM 进程，固定 512 MiB 堆。每个场景预热 1 秒，采集 7 个至少 100 ms 的样本；下表为每版 14 个样本的中位数。所有表格统计的是这些指定场景，不是服务器 TPS。

完整规划入口对比共同使用当前工作区的规划器字节码，替换的只有执行证明实现；相关共享类哈希记录在基准元数据中。`ExactCraftPlan` 使用 identity 键及 `Map.copyOf`，不同 JVM 可能把同一条执行链分成不同块。因此固定输入认证用例比较完整块与数量摘要；整条规划链用例独立核对每一步的顺序、数量、输入输出和总物料平衡，只忽略块分组边界。

## 验证与复测

新增验证包括 500 组含催化剂、容器和副产物的独立逐次执行对照，反序依赖和工作上限、调用方库存／次数不被修改、不同配方实例共享 source 时保持隔离、取消后重试，以及 2,000 组线性供应器选择与原稳定排序的对照。完整分发回归覆盖共享种子的单一归属、同容量并列顺序、UNBOUNDED 优先及普通复制预算；共享输入测试覆盖完整键比较、显式标记、后续输入变化。

开发阶段 `cleanTest build` 成功：112 个测试套件、864 项测试，0 失败、0 错误、0 跳过。两组基准的生产源码及驱动源码哈希与该阶段文件一致。该次全量构建包含工作区已有规划器改动，优化提交不包含那些改动。

原始开发工作区的复测命令如下；`591bfba` 是本地开发历史，远端 `alpha` 克隆请使用文末的整合前基线。

```sh
python3 scripts/runtime-hotpath-benchmark/run.py --suite big-execution --baseline-ref 591bfba
python3 scripts/runtime-hotpath-benchmark/run.py --suite batch --baseline-ref 591bfba
./gradlew --offline cleanTest build
```

汇总数据分别见 `docs/benchmarks/big-execution-20261022.json` 和 `docs/benchmarks/batch-hotpaths-20261022.json`。原始样本、源码哈希和 JVM 参数位于对应的 `build/big-execution-benchmark/`、`build/batch-hotpath-benchmark/`，不加入提交。
