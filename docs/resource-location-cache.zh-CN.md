# ResourceLocation 弱缓存

后续冷路径优化见 [冷路径复测](resource-location-cold-path.zh-CN.md)。本文保留首次实现的结构和测量快照；后续版本使用单弱节点主表并延后字符串索引。

接续 `f23ef2f` 的对象复用实验。改动仅在实验分支，未合入 alpha。

## 实现与兼容边界

- 复用已有 `WeakOpenHashMap`，以 RL 自身同时作为弱键和弱值。活着的 RL 自己保住内容键，调用方的字符串、快捷槽碰撞或扩容不会让它失去规范实例。并发首次创建在锁外运行原工厂，再原子选出一个代表。
- `namespace/path` 使用 4096 槽弱快捷索引，未命中查询内容表。完整字符串解析也有弱快捷索引；普通冒号解析另外用弱字符串键、弱 RL 值的别名表，避免大工作集反复切割字符串。自定义分隔符纳入快捷索引的匹配条件，仍由原版处理解析。
- 字符串别名只是加速。组合字符串被 GC 回收时可以丢失别名，但仍由 RL 内容表保证当前缓存代内的活对象复用。无强字符串池；服务端/客户端 tick 和插入路径按预算清理引用队列。
- 普通弱键查询直接比较原 key，避免为每次命中创建临时 Lookup。关闭缓存时在 Mixin 入口直接返回原工厂，避免进入多层缓存包装。
- 缓存命中只复用原工厂已接受的值；未命中仍调用原工厂。保留非法输入异常、try 工厂的 null、默认/空命名空间、withPath/prefix/suffix 和自定义分隔符语义。
- 不改原版 `equals`，hash 仍缓存原来的数值；不要求附属改用 `==`。缓存启用前、关闭期间、重载/清空前后的对象仍可用值相等和普通 HashMap 正确查找。缓存代次之间不承诺引用相同，绕过这些工厂的外部创建也不在身份保证范围内。
- 未改 TagKey 原生弱 interner、ResourceKey 原生 interner 或附属自定义键契约。
- 配置监视器重读完全相同的开关值时保留当前缓存；开关改变和显式 clear 才换代，旧代在途构造不会写入新代。

`thunderbolt-common.toml` 的 `[objects] reuseResourceLocations` 新默认值为 `true`；已有配置文件保存的 `false` 不会被强制覆盖，需要改为 `true` 才启用。关闭后走原工厂，不再建立上述索引。`cacheResourceHashes` 独立控制。

首次遇到新 ID 要创建弱引用节点、维护表和处理扩容，因此冷插入更贵，也需要额外索引内存。这不是对所有负载都更快的修改；反复使用同一批 ID 才能摊销成本。

## 基准方法

使用同一个外部 `ResourceLocationBenchmark`，原始对象基线 `3798e5b`、Lean `22d4c093`、当前 TB 开缓存、当前 TB 关缓存各三个独立 JVM；全部顺序执行，不并行争用。原始基线仍包含 TB 其他功能，并非移除整个 TB 的整包。

Minecraft 1.21.1 / NeoForge 21.1.219 / AE2 19.2.17 / Java 21.0.11 arm64。每 JVM 六轮预热、九轮测量，每轮二十万调用；冷插入每轮两万全新 ID，输入字符串在计时前生成。每格取三个 JVM 各自中位数的中位数，分配量来自 ThreadMXBean，不是存量堆大小。

8192 项工作集持有全部 RL 和输入字符串，保证比较的是已有活对象的重复命中。`parse_equal_string` 每次显式 new String，24 B 的输入对象属于调用方。哈希查找使用真正的 8192 项 HashMap，不再用不调用 hashCode 的单元素 Map.of。hash_map 使用已有键查询，不能解读成整个反序列化/独立键查找流程的成本。

本轮是专门的 RL 循环，与之前全场景混合基准的 JIT 上下文不同，不能把数字直接混填进旧完整表。所有进程中位数、分配量及源码/日志指纹见[配套 JSON](resource-location-cache-results.json)。原始基线和 Lean 各运行三次；TB 收尾消除临时查询分配和关闭路径包装开销后，两种模式各重新运行三次。表中全部 TB 数字使用最终实现。

## 结果

每格为 **ns/次；分配 B/次**。

| 场景 | 原始对象基线 | Lean | TB 开启 RL 缓存 | TB 关闭 RL 缓存 |
| --- | ---: | ---: | ---: | ---: |
| 重复解析完整字符串 | 39.81；144 | 25.71；120 | **3.72；0** | 44.32；144 |
| 重复 namespace/path 工厂 | 14.57；24 | 9.30；0 | **4.86；0** | 14.51；24 |
| 每次 new 等值输入字符串后解析 | 38.63；168 | 27.23；144 | **6.04；24** | 41.30；168 |
| 8192 个活 ID 轮换解析 | 27.64；128 | 55.23；104 | **11.78；0** | 27.32；128 |
| 首次创建全新 ID | **13.94；24** | 93.70；64 | 128.91；200 | 15.20；24 |
| 已有 RL 的 hashCode | 1.62；0 | 0.83；0 | 0.78；0 | 0.92；0 |
| 已有键查询 8192 项 HashMap | **3.97；0** | 6.81；0 | 5.94；0 | 10.11；0 |

收益集中在重复工厂/解析，尤其避免子串分配；首次插入付出额外代价。预建 HashMap 行没有表现出普遍加速，且 TB 开关两组原生 hash/equals 代码相同，仍出现较大的进程/JIT 差异，不能把这个差值归因于关闭开关本身或据此推算整包性能。弱引用缓存仍有索引节点、表容量及清理成本，分配量不代表最终存活内存。

## 验证

新增五项实际 Mixin GameTest，覆盖 12000 个活 ID/快捷槽碰撞/扩容、真实同 hash 不同内容、各种工厂/分隔符/校验/HashMap、八线程首次创建、在途工厂与重置隔离、调用方字符串与未使用 RL 的 GC 回收。另运行全量 JUnit 和含七个 AE 附属的对象兼容性 GameTest。

最终结果：**867 项 JUnit、36 项 GameTest 全通过，jar 构建通过**。使用全新游戏目录确认生成配置默认 `reuseResourceLocations = true`，同时验证首次写配置后的监视器重读不会无故丢弃缓存。七个附属共校验 807 个物品，另校验 12 种已注册流体；这是这些受测版本和场景的兼容证据，不等于覆盖全部整包行为。

复测命令使用已有外部 harness，加上 `-PcomparisonResourceOnly=true`；`comparisonMode` 为 BASE、LEAN、OURS、OURS_OFF。OURS/OURS_OFF 在测量开始时显式设置开关，避免被测试目录残留配置影响。用 `scripts/benchmarks/object-reuse/summarize-resources.py <日志目录> <输出 JSON>` 汇总；脚本要求每个模式三份成功完成的 GameTest 日志。
