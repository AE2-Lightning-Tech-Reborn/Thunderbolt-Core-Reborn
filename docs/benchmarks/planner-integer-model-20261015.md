# TB v2：用精确整数模型替换最后一层混批枚举

基线为 `35ffe46f994dd2b0c922aa4bba9dd3d63f98516a`。本轮改动针对现有 3～6 路普通原料混批求解，以及两路求解器重复的整数边界处理。没有扩大支持域、调高工作上限，也没有删除通用规划器的搜索阶段。

`MultiRouteBatchOptimizer` 固定总执行次数并逐路枚举数量。到最后两路时，只剩 `x + y = L` 一个自由整数变量。设当前前缀产量为 `P`，两路产量为 `a、b`，剩余原料为 `Rᵢ`，两路对原料 i 的消耗为 `uᵢ、vᵢ`，则原问题严格等价于：

```text
0 ≤ x ≤ L
(b - a) x ≤ P + bL - demand
(uᵢ - vᵢ) x ≤ Rᵢ - vᵢL    对每种原料分别成立
y = L - x
```

这些约束的整数解是一个区间，可能为空。总原料消耗也是 x 的线性函数：斜率为负时取上端点，否则取下端点。零斜率时取较小 x，保持原先递增枚举的平局顺序。因此，在搜索完成的情况下，执行次数、库存消耗和配方身份选择均与完整枚举一致。所有计算继续使用 `BigInteger`，最终仍按原始配方和原始资源约束重建证书。

新增的 `IntegerInterval` 统一处理正、负、零斜率和带符号除法的取整，供 `PairBatchAllocation`、`TwoRouteBatchOptimizer` 和上述尾部求解共同使用。两路求解仍保留各自既有的平局规则。固定系数只在一次搜索内准备，没有跨请求缓存。

若有 r 路、固定总次数 T，完整枚举的叶子数量为 `C(T+r-1, r-1)`；解析最后两路后，尾部求解次数降为 `C(T+r-2, r-2)`，每次处理有限数量的资源约束。实际运行仍受原来的 16,384 工作单位上限控制。解析节点同时为区间约束和库存目标计费，避免把更重的节点仍当成普通叶子。预算用尽继续返回已有可行方案，不能宣称搜索完成。额外常驻数据为 O(原料种类数)，没有按请求数量分配的大数组。

代码量并未大幅减少：受影响生产代码从 460 行变为 484 行，按现有 AST 统计器计算的分支点均为 187。收益是少一层组合枚举和一份统一的整数边界实现；增加的代码主要是系数准备和证明注释。没有将代码搬到别处后把搬走的行数当成删除量。

验证结果：

- 完整测试集：1292 项，0 失败、0 错误、2 项沿用原配置跳过。随后加入冻结的 40→26 次回归用例，相关 13 项测试再次全部通过。
- 混批独立穷举对照扩展到 1200 个 3～6 路小图；共享区间另有 50,625 组带符号双约束穷举，以及超出 long 范围的系数检查。
- 8192 个额外混批样本全部通过原始配方身份、逐资源消耗和 `MaterialDagReplay` 检查。原先完成的 7006 个结果完全相同，完成数量增至 7356；没有执行次数增加或相同执行次数下总原料消耗增加。4 个此前未完成的样本分别从 40→26、51→19、37→15、57→15 次执行。
- 3339 个公开规划器样本：可行性、执行次数、各库存消耗、缺失量和预算标志全部一致，并通过独立物料平衡及逐次执行回放。
- 最终 JAR 内 505 个生产 class 与已验证编译输出逐字节一致。JAR 的 SHA-256 和生产源码哈希见同名 JSON。

性能测试按基线、候选、候选、基线串行运行，每组使用新 JVM（Java 21，`-Xms256m -Xmx1g`）。混批与两路测试均包含 512 个不同样本，预热 20 轮、测量 10 轮；表中为每臂两次运行的总量均值。它们是离线求解测量，不能换算为服务器 TPS。

| 工作负载 | 基线耗时 | 候选耗时 | 基线分配量 | 候选分配量 |
| --- | ---: | ---: | ---: | ---: |
| 3～6 路混批，5120 次 | 447.3 ms | 326.1 ms | 3.639 GB | 2.744 GB |
| 两路求解，5120 次 | 22.80 ms | 22.72 ms | 62.46 MB | 56.09 MB |
| 公开规划器，3339 次 | 8.537 s | 8.512 s | 16.566 GB | 16.510 GB |

混批压力集平均耗时下降 27.1%，分配量下降 24.6%，工作计数下降约 16.0%。两路和公开规划器耗时差异很小，应视为未测出明显变化；两路结果及工作计数完全一致。这里只有每臂两次进程测量，不能当作广泛性能保证。

另试验过以 Fenwick 前缀最小值替换终端优化器的支配边界维护。虽然相关行为测试通过，但已知用例工作计数从 2738 增至 2774，更紧预算下可能失去旧收益，因此未纳入本次改动。终端优化器保留原实现。

复现需要 Java 21 和已解析的 Gradle 依赖。在仓库根目录执行：

```sh
./gradlew testClasses -I scripts/benchmarks/test-classpath.init.gradle \
  -PplannerAuditClasspath=/tmp/tb-model-classpath.txt writePlannerAuditClasspath --offline
python3 scripts/benchmarks/compare-planner-models.py \
  --classpath-file /tmp/tb-model-classpath.txt --output /tmp/tb-model-comparison
```

脚本从指定 Git 基线编译隔离覆盖类，不修改生产源码；包含独立回放、已完成结果完全一致及目标退化检查。8192 样本扩展检查使用同一 `BatchSearchAudit`，设置 `-Daudit.samples=8192 -Daudit.warmupRounds=0 -Daudit.measurementRounds=1`，分别把脚本产出的基线覆盖类或候选类置于 classpath 前部。完整记录的摘要和 CSV 哈希保存在 `planner-integer-model-20261015.json`。
